high
Comprehensiveness
Browser size errors on a retry can leave callback requests unsettled

Do not clear `_endCalled` during the internal `_retry()` path, or make the browser size-abort path invoke the callback independently of that flag. For example, make the first browser XHR return 500 and the retried XHR return a 100-byte 200 response for `request.get(url).retry(1).maxResponseSize(10).end(callback)`. The first callback enters `_retry()`, which now sets `_endCalled` to false. The retried terminal response calls `_abortWithSizeError('response')`, but its `if (this._endCalled && !this.called)` guard then suppresses `callback(error)`. The ready-state handler also returns for the aborted size-error request, leaving the supplied callback uncalled.

Evidence: The description promises, “When a request or response body exceeds its configured limit, abort immediately with an Error (`code = 'ETOOLARGE'`).” The patched `src/request-base.js` `_retry()` clears `_endCalled`, while the added `src/client.js` `Request.prototype._abortWithSizeError()` only calls `callback` when `_endCalled` is true.

high
Comprehensiveness
Size errors omit `err.retries` when retry was never configured

Assign `error.retries = 0` unconditionally for every `ETOOLARGE`/size-error path in both callback implementations. Currently the assignment is nested under `_retriesConfigured || _maxRetries !== undefined`. Thus `request.post(url).maxRequestSize(1).send('xx').end((err) => err.retries)` receives an `ETOOLARGE` error whose `retries` is `undefined`, not `0`; the same occurs for ordinary response-limit errors without `.retry()`.

Evidence: The description explicitly requires, “Size errors must never trigger automatic retries (`err.retries` is 0).” The patched `src/client.js` and `src/node/index.js` callbacks set `error.retries = 0` only when `_retriesConfigured` or `_maxRetries` is defined.

high
Comprehensiveness
Browser response limit treats unsupported compression codings as identity

Classify every non-identity `Content-Encoding` as encoded for sizing purposes when XHR supplies a decoded representation, rather than recognizing only `gzip`, `deflate`, and `br`. A same-origin XHR with `Content-Encoding: zstd`, `Content-Length: 50`, a decoded 5000-byte ArrayBuffer, and `maxResponseSize(100)` reaches the terminal check with `isEncodingEstablished` true and `isCompressed` false. That makes `isKnownIdentity` true and selects the 50-byte wire length, allowing an oversized decoded response.

Evidence: The browser requirement is: “Evaluate decoded payload size for compressed responses, even if Content-Encoding is unexposed.” In the added terminal response logic in `src/client.js` (the hunk beginning at new line 1102), `isCompressed` only matches `gzip|deflate|br`, but `isKnownIdentity` is true for any exposed encoding that did not match that expression.

medium
Code Quality
Internal retry resets externally meaningful end state

Remove `_endCalled = false` from shared `_retry()`. It is unnecessary because `_retry()` calls `_end()` directly, and it changes behavior after a Node request initiated with `.end()`: on a successful retry, `_emitResponse()` no longer installs its guard that makes `response.pipe()` throw because `.end()` was already used. Keep `_endCalled` as the record of the public call and only reset per-attempt transport state.

Evidence: Patched `src/request-base.js` resets `_endCalled` immediately before `return this._end()`. `src/node/index.js` `_emitResponse()` uses `_endCalled` to install the explicit “end() has already been called, so it's too late to start piping” guard.

Feedback

The shared API additions and most of the transport coverage are substantial: the patch correctly centralizes the limits in the base request type, handles Node multipart replay when retries are enabled, preserves the direct-streaming multipart path without a request limit, and adds browser multipart serialization with a matching boundary. It also deliberately avoids the old double-callback behavior and handles the tested bodyless-response cases.

Please correct the retry lifecycle before relying on this implementation. An internal retry must not erase the fact that the user called `.end()`, particularly because the browser size-abort callback currently depends on it. Make `retries` consistently zero for all size errors, not merely errors from requests that called `.retry()`, and make compressed-response sizing conservative for all non-identity content codings. Those changes would close the uncovered size-limit bypasses while retaining the intended streaming and replay behavior.
