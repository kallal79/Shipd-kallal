Explicit browser text mode bypasses BOM-aware CORS compressed-response limits

Do not leave responseType('text') on the XHR when a response-size limit needs exact decoded-entity accounting. For a cross-origin gzip response whose unexposed Content-Encoding is transparently decoded from EF BB BF 61 to responseText/response === 'a', getRawXhrByteLength() is undefined and getTextDecodedByteLength() returns 1. Both the progress and terminal ambiguous-compression paths use that value, so maxResponseSize(1) succeeds instead of raising ETOOLARGE for the four-byte entity. Retain a binary representation for the size check (and reconstruct the requested text response), including for explicit text mode, so a decoder-consumed BOM remains countable.

Evidence: The description promises: "Measure decoded text sizes for compressed responses honoring BOM markers ... even when CORS unexposes Content-Encoding." In the added src/client.js responseType setup, isExplicitText prevents _forcedArrayBufferForSize; the added getRawXhrByteLength() only recognizes binary response values, while getTextDecodedByteLength('a', ...) returns one UTF-8 byte. The added ambiguous/unexposed Content-Encoding terminal branch selects decodedBytes rather than wireBytes.

high
Code Quality
A limited unbuffered response is no longer readable from the documented end callback

Preserve the established .buffer(false) callback-stream contract. The new unbuffered branch calls _emitResponse() before callback delivery (which attaches a raw data listener), then, when _maxResponseSize is set, calls res.resume() and waits for raw end before callback(null, response). Thus an in-limit multi-chunk response has already emitted all data and end before an end callback can attach res.on('data') or res.on('end'). Expose a monitored stream before it starts flowing, or provide a documented buffered/replayable response strategy; do not silently hand the callback an exhausted stream.

Evidence: The existing documented test example at docs/test.html:2709-2755 uses .buffer(false).end((error, res) => { res.on('data', ...); res.on('end', ...); }). The base implementation at src/node/index.js:1191-1209 invokes that callback immediately on headers. The patch's new src/node/index.js unbuffered branch (the hunk beginning at patched line 1751) emits the response first, resumes it for every limited response, and invokes callback only in res.once('end').

Feedback

The patch is in scope: it changes only production sources, and its common path is thoughtfully wired through the shared RequestBase API, retry sentinel, Node redirect/decompression paths, and browser request preflight. It also correctly avoids obvious Content-Length false positives for the listed bodyless response statuses in the covered paths.

Two untested public paths remain unsafe. Exact browser accounting is lost for explicit text XHR responses when the browser consumes a BOM, precisely where CORS hides compression metadata. Separately, the Node solution achieves final callback timing by consuming limited unbuffered responses before the callback can observe them, which breaks the repository's documented streaming usage. Address both before merging, with tests for cross-origin explicit-text BOM input and for attaching data/end listeners inside an in-limit .buffer(false).maxResponseSize(...).end callback.
